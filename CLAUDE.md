## 1. What this project is

A **100 % client-side** sudoku puzzle generator and PDF exporter built with Next.js.
No backend, no database, no external API calls — everything runs in the browser.

- Users choose a difficulty (1–10) and a grid count (1–99)
- Grids are generated by a backtracking algorithm in the browser
- The PDF is built locally via jsPDF (lazy-loaded on demand) and saved to disk
- Up to 20 grids are previewed in the browser; all grids are always included in the PDF

**Deployment target**: Vercel (static, auto-detected as Next.js).

## 4. Tech stack — exact versions and constraints

| Package | Version | Notes |
|---|---|---|
| `next` | `^16.1.6` | Turbopack by default (dev + prod) |
| `react` | `^19` | Must stay in sync with react-dom |
| `react-dom` | `^19` | Must stay in sync with react — mismatching caused Vercel ERESOLVE (ADR-008) |
| `jspdf` | `^4.2.0` | Lazy-loaded via `await import('jspdf')` — **do not change this pattern** |
| `tailwindcss` | `^4.2.1` | v4 — config-free, `@import "tailwindcss"` in CSS |
| `@tailwindcss/postcss` | `^4.2.1` | Required adapter for Tailwind v4 + PostCSS |
| `eslint` | `^9` | **Pinned to ^9** — eslint-config-next is incompatible with ESLint 10 (ADR-007) |
| `eslint-config-next` | `^16.1.6` | Must match next version |
| `postcss` | `^8` | Required by @tailwindcss/postcss |

**DO NOT:**
- Bump `eslint` to `^10` — the bundled `eslint-config-next` parser crashes with `ScopeManager.addGlobals` (see ADR-007)
- Split `react` and `react-dom` to different major versions — causes Vercel peer-dep failures
- Add `autoprefixer` — it is bundled inside Tailwind v4
- Add `tailwind.config.mjs` — v4 auto-detects content, no config file needed
- Add `tailwind.config.js/ts` unless introducing custom theme tokens

## 5. Import paths and module system

The project is `"type": "module"` (ES Modules throughout). Always use ESM syntax:

```js
import { generateSudoku } from '@/lib/sudoku';  // ✓  path alias (@/* → ./*)
import { generateSudoku } from '../lib/sudoku';  // ✓  relative path also valid
const { generateSudoku } = require('../lib/sudoku'); // ✗  CJS require not valid
```

The `@/*` alias is configured in `jsconfig.json` and works in both `app/` and `lib/`.

## 6. Core algorithm — lib/sudoku.js

This file is **pure JavaScript with zero imports**. It exports three functions:

### `generateSudoku(difficulty: number): { puzzle: number[][], solution: number[][] }`

1. Builds a fully-solved 9×9 board via `solve(board, shuffleNums=true)`
2. Removes `round(25 + (difficulty - 1) * 3.67)` cells at random positions
3. Returns both the puzzle (with 0s for empty cells) and the full solution

**Known limitation (open TODO)**: uniqueness of the puzzle solution is not verified.
The cells are removed randomly. A correct implementation would call `solve()` again
after each removal to confirm exactly one solution remains.

### `getDifficultyLabel(d: number): string`

Maps 1–10 to French labels: `Tres facile` / `Facile` / `Moyen` / `Difficile` / `Tres difficile` / `Expert`.

### `drawGridOnPDF(doc: jsPDF, board: number[][], x, y, size): void`

Draws one sudoku grid onto an existing jsPDF document at the given coordinates.
Called from `app/page.js` during PDF export. The function is in `lib/` rather than
`app/` so it can be tested without a DOM environment.

## 7. UI — app/page.js

The entire UI is a single `'use client'` component with three sub-components:

| Component | Purpose |
|---|---|
| `Home` (default export) | State management, controls, PDF export logic |
| `SudokuGrid` | Renders one 9×9 puzzle as a CSS grid of divs |
| `DifficultyBar` | 10-segment colour gradient reflecting the current difficulty |

**State in `Home`:**
- `difficulty` (1–10), `gridCount` (1–99): controls
- `grids`: array of `{ puzzle, solution }` objects from `generateSudoku`
- `isGenerating`, `isExporting`, `exportProgress`: UI loading states
- `includeSolutions`: checkbox toggle

**PDF export pattern** — jsPDF is always lazy-loaded:
```js
const { jsPDF } = await import('jspdf');
```
This keeps the initial JS bundle small. **Do not move this to a top-level import.**

**Generation pattern** — uses a 30 ms `setTimeout` to flush React's re-render
(show the "Generating…" button label) before the synchronous backtracking loop
blocks the thread. This is a known limitation; the correct fix is a Web Worker
(tracked in TODO.md as a critical item).

## 8. Styling — Tailwind v4

`app/globals.css` uses the Tailwind v4 single-import pattern:

```css
/* ✓ Correct — Tailwind v4 */
@import "tailwindcss";

/* ✗ Wrong — Tailwind v3 directives */
@tailwind base;
@tailwind components;
@tailwind utilities;
```

`postcss.config.mjs` uses `@tailwindcss/postcss`, not `tailwindcss`:

```js
// ✓ Correct
plugins: { '@tailwindcss/postcss': {} }

// ✗ Wrong — Tailwind v3 plugin
plugins: { tailwindcss: {}, autoprefixer: {} }
```

Inline styles (`style={{ ... }}`) are used alongside Tailwind where Tailwind
utility classes would be too verbose (e.g., dynamic border widths in the grid cells,
gradient backgrounds). This is intentional; do not remove inline styles in favour
of arbitrary Tailwind values unless there is a clear readability gain.

## 9. HTTP security headers — next.config.mjs

Security headers are applied to every route via the `headers()` async function in
`next.config.mjs`. The current policy:

| Header | Policy |
|---|---|
| CSP | `default-src 'self'`, scripts/styles `'unsafe-inline'`, workers/images `blob:` |
| `X-Frame-Options` | `DENY` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | camera/mic/geo/payment all disabled |

**CSP notes for future work**:
- `unsafe-eval` is present because Next.js / Turbopack requires it.
- `unsafe-inline` is required by Tailwind CSS v4's runtime style injection.
- A nonce-based CSP would remove both `unsafe-*` directives but requires a custom
  Next.js middleware — deferred to a future iteration.

## 10. Testing

Tests live in `tests/sudoku.test.js` and use the built-in `node:test` module (no
Jest, no Vitest, no extra dependencies).

```bash
npm test
# Output: TAP, 21 tests, all must pass
```

**Test coverage:**
- `generateSudoku`: shape, validity, cell values, difficulty curve, randomness
- `getDifficultyLabel`: all 10 difficulty levels

**What is NOT tested (known gaps, see TODO.md):**
- `drawGridOnPDF` — requires a jsPDF instance (no DOM/Canvas in Node.js test environment)
- `app/page.js` — React component, no `@testing-library/react` setup exists yet

**When adding new logic to `lib/sudoku.js`, always add a corresponding test.**
When fixing a bug, write the failing test first, then fix the code.

## 11. Git workflow and commit conventions

### Branch naming
All AI-generated branches **must** start with `claude/`:
```
claude/short-description-sessionid
```
This prefix triggers `claude-auto-merge.yml` which auto-approves the PR and enables
squash-merge once CI is green.

### Commit message format (enforced by CI on PR titles)
```
<type>(<optional-scope>): <description>
```

Valid types: `feat` · `fix` · `docs` · `style` · `refactor` · `test` · `chore` · `perf` · `ci` · `build` · `revert`

**Examples from this repo:**
```
feat: add PDF compression
fix(pdf): correct grid alignment on A4
chore: update jspdf to v4.3
docs: add offline usage instructions
test: add edge cases for difficulty 10
ci: fix release-please PR URL in release.yml
refactor: extract grid generation to useGridGenerator hook
```

### Push workflow
```bash
git push -u origin claude/<branch-name>
# If rejected (remote has new commits):
git pull origin claude/<branch-name> --rebase
git push -u origin claude/<branch-name>
```

**Never force-push.** If a rebase produces conflicts in `package-lock.json`,
accept the remote version (`git checkout --theirs package-lock.json`) then run
`npm install` to regenerate it, then re-stage and continue the rebase.

## 12. CI/CD — GitHub Actions overview

### Workflows triggered on push/PR

| Workflow | Trigger | Purpose |
|---|---|---|
| `ci.yml` | push to main/develop, PRs | Lint → Test → Build (blocking) |
| `pr-check.yml` | PR opened/edited/sync | Validate PR title (Conventional Commits) |
| `claude-auto-merge.yml` | PR from `claude/*` branch | Auto-approve + enable squash auto-merge |
| `dependabot-auto-merge.yml` | PR from `dependabot[bot]` | Auto-approve + enable squash auto-merge |

### Workflows triggered on schedule/dispatch

| Workflow | Schedule | Purpose |
|---|---|---|
| `security.yml` | Weekly (Monday 09:00 Paris) | npm audit + CodeQL scan |
| `release.yml` | Push to `main` | release-please creates release PR and/or GitHub Release |

### Auto-merge behaviour
1. Claude opens a PR from a `claude/*` branch
2. `claude-auto-merge.yml` runs: approves + calls `gh pr merge --auto --squash`
3. GitHub queues the merge; it fires automatically when `Lint · Test · Build` is green
4. `release.yml` fires on the resulting push to `main`; release-please creates/updates a release PR
5. When the release PR is merged, a GitHub Release + tag is created automatically

### Required GitHub settings (one-time manual setup)
- Settings → Actions → General → **Allow GitHub Actions to create and approve pull requests** ✓
- Settings → General → Pull Requests → **Allow auto-merge** ✓
- Branch protection on `main`: require PR + require `Lint · Test · Build` + `PR checks passed`

## 13. Dependency management principles

This project deliberately minimises dependencies. Before adding any package:

1. Ask: can this be done with ~10 lines of vanilla JS? (For this project, usually yes)
2. Check if it's already available in Next.js / React (e.g., `node:test` instead of Jest)
3. Prefer zero-config packages over highly configurable ones
4. Always use `npm install --save-dev` for dev-only tools

**Current production dependency count: 4** (`next`, `react`, `react-dom`, `jspdf`)
**Dev dependency count: 5** (`@tailwindcss/postcss`, `eslint`, `eslint-config-next`, `postcss`, `tailwindcss`)

## 17. Docker

### How the build works

The project uses a **three-stage** Docker build to keep the final image small:

| Stage | Base | Purpose |
|---|---|---|
| `deps` | `node:20-alpine` | `npm ci` — layer cached until lockfile changes |
| `builder` | `node:20-alpine` | `next build` — produces `.next/standalone/` |
| `runner` | `node:20-alpine` | Copies only the standalone output; runs as `nextjs` (non-root) |

`next.config.mjs` must contain `output: 'standalone'` — this is already set.
The standalone build produces `server.js` + a minimal `node_modules` subset;
the full 200+ MB dev node_modules are not copied into the runtime image.

### Runtime directory layout (inside container)

```
/app/                     ← WORKDIR
├── server.js             ← Next.js standalone entry point
├── node_modules/         ← minimal subset (~25 MB) from standalone build
├── public/               ← static public assets (currently empty)
└── .next/
    └── static/           ← compiled JS/CSS chunks
```

### Commands

```bash
# Build image
docker build -t sudoku-generator .

# Run
docker run -p 3000:3000 sudoku-generator
# → http://localhost:3000

# With compose
docker compose up --build    # build + start
docker compose up -d         # background
docker compose down          # stop + remove
docker compose logs -f       # follow logs
```

### Health check

The Dockerfile includes a `HEALTHCHECK` that polls `http://localhost:3000/` via
a Node.js one-liner — no extra tools (curl/wget) are installed in the Alpine image.

### Key files

| File | Purpose |
|---|---|
| `Dockerfile` | Multi-stage build definition |
| `.dockerignore` | Excludes `node_modules/`, `.next/`, `.env*`, `.git/`, `*.md` from build context |
| `docker-compose.yml` | Production compose with `restart: unless-stopped` |
| `public/.gitkeep` | Keeps `public/` tracked by git — Docker COPY requires the directory to exist |

### What NOT to do with Docker

- Do not add secrets to `docker-compose.yml` — use `.env` files mounted at runtime or Docker secrets
- Do not commit `.env` files — `.dockerignore` already excludes them
- Do not remove `output: 'standalone'` from `next.config.mjs` — the runner stage depends on it
- Do not change the `USER nextjs` line — running as root in containers is a security risk

## 18. setup.sh

A single script that prepares the project for development or deployment.

```bash
./setup.sh              # install deps + lint + test + build  (mirrors CI)
./setup.sh --docker     # same + build Docker image
./setup.sh --skip-ci    # install deps only
./setup.sh --help       # usage reference
```

**What it does:**
1. Checks Node.js >= 20 and npm >= 10 (exits with error if not met)
2. Checks Docker daemon is running (only with `--docker`)
3. Runs `npm install`
4. Runs the full CI pipeline: `npm run lint && npm test && npm run build`
5. Optionally runs `docker build -t sudoku-generator:latest .`
6. Prints a summary of useful commands

**The script is idempotent** — safe to run multiple times without side effects.
Colors are disabled automatically when stdout is not a TTY (safe in CI logs).

## Shared conventions (BCIT-Formation)

These rules apply to every BCIT-Formation repository. The canonical version lives in
[claude-skills-bcit/CONVENTIONS.md](https://github.com/BCIT-Formation/claude-skills-bcit/blob/main/CONVENTIONS.md).
Repo-specific sections in this file may add stricter rules, never weaker ones.

### Git
- Never commit directly to the default branch; one branch per task, delivered as a PR.
- Branch naming: `claude/<short-topic>` for AI-agent work, `feat/<topic>` or `fix/<topic>` otherwise.
- Conventional Commits: `type(scope): imperative lowercase subject` (72 chars max).
  Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- Never force-push shared branches; never bypass hooks (`--no-verify`). Stage specific files rather than a blanket `git add -A`.
- Squash-merge by default.

### Security (non-negotiable)
- Never commit secrets, tokens, API keys, or personal data. Secrets live in `.env` (gitignored); commit `.env.example` with placeholders only.
- Validate and sanitize all external input. SQL only through parameterized queries, never string concatenation.
- No sensitive data in logs; use placeholders like `[REDACTED]`.
- Least privilege everywhere; HTTPS for all network calls.

### Dependencies
- Keep dependencies minimal; prefer the standard library and dependencies already present.
- A new production dependency needs a clear justification recorded in `DECISIONS.md` (or `docs/ADR.md`).

### Code quality
- Match the surrounding code style; produce the smallest diff that solves the problem (KISS, DRY, YAGNI).
- Comments explain WHY, not WHAT.
- Never merge TODO/FIXME markers, temporary mocks, or incomplete implementations to the default branch.

### Testing
- Every bug fix gets a regression test; write the failing test first.
- New or changed logic gets matching tests. Run this repo's documented lint/test commands before committing.

### Documentation
- CLAUDE.md contains durable instructions only: no status reports, changelogs, or task lists (those live in `TODO.md` / `CHANGELOG.md`), and no session-specific branch names or URLs.
- Record architecture decisions in `DECISIONS.md` / `docs/ADR.md`; read it before changing fundamentals, and do not re-fix items already resolved there.
- If documentation contradicts the code or itself, flag the inconsistency instead of silently picking a side.

### Language
- Team language is French: user-facing content and business documents are written in French.
- Code identifiers are in English. For docs, comments, and commits, match the repo's existing language.

### AI assistant behavior
- Never invent APIs, endpoints, data models, metrics, or quotes. If required business information is missing, stop and ask one precise question.
- Ask before: deleting files, major refactors, changing dependencies, or any force-push.
